## Task 1: Fix #702 — FK violation on threat-model create must not blacklist the caller's token

### Issue #702: fix(api): any FK violation on threat-model create blacklists the caller's valid token and forces re-login

## Summary
`CreateThreatModel` (api/threat_model_handlers.go:286-303) treats **any** foreign-key constraint violation as proof that the authenticated user no longer exists, then **blacklists the caller's bearer token** and returns 401 "Your session is no longer valid. Please log in again."

The inference is wrong. `isForeignKeyConstraintError` (api/request_utils.go:669) matches any FK error — typed `dberrors.ErrForeignKey` or a substring match — with no check of *which* constraint failed. A threat model has FKs to several parents besides the owning user.

Observed live on Oracle ADB while seeding CATS fixtures:

```
Failed to create threat model: foreign key: constraint violation:
ORA-02291: integrity constraint (ADMIN.FK_THREAT_MODEL_ACCESS_GROUP) violated - parent key not found
Foreign key constraint violation for user charlie@tmi.local - invalidating session
```

`FK_THREAT_MODEL_ACCESS_GROUP` is the **authorization group** reference — the request named a group that does not exist. The user row was present and valid the whole time. The server nevertheless destroyed that user's session.

## Steps to Reproduce
1. Authenticate as any user.
2. `POST /threat_models` with an `authorization` entry referencing a group UUID that does not exist.
3. Observe: 401, and the bearer token is now blacklisted — every subsequent request with it fails until the user logs in again.

## Expected Behavior
A request referencing a non-existent group is a client error about that request: **400/422** (bad reference) or 404. The caller's session must not be touched.

## Actual Behavior
The valid token is blacklisted and the session is destroyed, so unrelated in-flight work by that user also fails.

## Impact
- **Availability/security**: any authenticated user can be logged out by a single request that trips any FK on this path. Because the bad reference is supplied *in the request body*, a client bug — or a malicious request from a low-privilege user against their own session — reliably nukes a session. It is a self-inflicted DoS primitive, and it destroys unrelated concurrent work under the same token.
- **Correctness**: an undocumented 401 on a path whose failure is really a 4xx about the payload (see the documented-status-code policy).
- It broke CATS fixture seeding against Oracle: the seeder lost its credential mid-run at entry 16 of 43.

## Possible Fix
1. Narrow the "user is gone" inference to the FK that actually implicates the user. Prefer an explicit existence check on the user row before concluding the session is dead, rather than inferring identity state from an arbitrary constraint name.
2. Map every other FK violation to a 400/422 that names the offending reference.
3. Blacklisting the caller's token is a heavy, irreversible side effect — it should require positive evidence the user is gone, never a heuristic. Consider removing the blacklist step entirely and letting normal token expiry handle the deleted-user case, which the JWT middleware already covers.
4. Audit other call sites of `isForeignKeyConstraintError` for the same over-broad inference.

## Notes
Not Oracle-specific in principle — PostgreSQL's `violates foreign key constraint` matches the same branch — but it surfaced on Oracle. Related Oracle work: #696, #698, #699, #701.

## Environment
Oracle ADB 23ai, branch dev/1.8.1/backlog-batch @ 992f70b0, found 2026-08-07 during the Oracle CATS pass.

**Direction for this task:** implement the issue's Possible Fix items 1-3: replace the blanket FK→"user is gone" inference in `CreateThreatModel` (api/threat_model_handlers.go) with (a) a positive existence check on the user row before ever concluding the session is dead, (b) mapping other FK violations to a 400 (or 422 only if already documented) client error naming the offending reference, and (c) removing token blacklisting unless there is positive evidence the user row is gone. Audit other call sites of `isForeignKeyConstraintError` (item 4) and fix any with the same over-broad inference. Check the OpenAPI spec documents the status code(s) you return for this operation (documented-status-code policy); if a needed code is missing from the spec for createThreatModel, add it and regenerate. Add/adjust unit tests covering: FK violation on a non-user constraint returns 4xx and does NOT invalidate the session; user-gone path still handled.

## Task 2: Fix #701 — Oracle admin-config lookup scans empty, duplicating the admin USERS row

### Issue #701: fix(server): Oracle admin-config lookup scans empty, creating a duplicate admin USERS row on every server start

## Summary
On Oracle, `findUserByProviderIdentityGorm` (cmd/server/main.go:2433) returns an error for a user that **does exist**, and the caller interprets that as "user doesn't exist" and creates the user again. Because `users` has no unique index on the provider identity, the insert succeeds — so every server start adds another duplicate row for each configured administrator, and the Administrators group grant attaches to the newest UUID.

Root cause is the #699 bug class: GORM matches result-set labels to scan-struct fields case-sensitively, and Oracle returns labels UPPERCASE. The scan target here is an ad-hoc struct with a hardcoded lowercase tag:

```go
var user struct {
    InternalUUID string `gorm:"column:internal_uuid"`   // never matches Oracle's INTERNAL_UUID
}
```

`First(&user)` succeeds and finds the row, but `user.InternalUUID` stays `""`, so the function's final `uuid.Parse(user.InternalUUID)` returns an error. At main.go:2361-2363 **any** error routes into the create branch.

Note this function was already hardened twice for the same dialect-casing problem — predicates go through `api.ColumnMap` (#503) and the table name through `TableName()` (#504). The `Select` projection and its scan struct are the remaining gap.

## Steps to Reproduce
1. Run against Oracle ADB (`make dev-up DB=oracle CLUSTER=docker-desktop`)
2. Configure an administrator with `subject_type: user` and a non-empty `provider_id` for a user that already exists in `USERS`
3. Restart the server two or more times
4. `SELECT provider, provider_user_id, COUNT(*) FROM users GROUP BY provider, provider_user_id HAVING COUNT(*) > 1` — the count grows by one per start

## Expected Behavior
An existing administrator is found and reused; no new row is written.

## Actual Behavior
A duplicate `USERS` row is created on every start, unbounded, with the admin grant on the newest UUID.

## Evidence / confidence
Not directly reproduced: this repo's dev config declares no `administrators:` entries (the auto-promotion path runs instead), so the code path is unexercised locally. The finding is from the oracle-db-admin review of #699 and rests on a mechanism **proven live** in the sibling site: `GetGroupsForUser` used the identical lowercase-tag pattern and returned correctly-counted rows with every field blank on Oracle (fixed in 992f70b0 on dev/1.8.1/backlog-batch). The failure mode here is the same mapping failure plus an error-swallowing caller.

## Impact
Duplicate identities for privileged accounts, unbounded table growth across restarts, and admin group membership attached to a row that later logins may not resolve to. This is exactly the orphan-duplicate outcome the comment at main.go:2369-2379 was written to prevent. Oracle is the production target.

## Possible Fix
1. Scan into `models.User` (a parsed model gets dialect-correct DBNames) instead of the ad-hoc struct — same fix as 992f70b0.
2. Independently, stop treating every lookup error as not-found at main.go:2361: distinguish `gorm.ErrRecordNotFound` from any other error, and never create on an unexpected error.
3. Make the existing `idx_users_provider_lookup` index UNIQUE so a mapping bug can never silently duplicate an identity again. This is a one-tag change in `api/models/models.go`:35-36 — the composite index over `(provider, provider_user_id)` already exists and is merely non-unique; switch both tags to `uniqueIndex:idx_users_provider_lookup`. There are **no existing Oracle deployments**, so no dedup pass, migration, or coexistence strategy is needed — AutoMigrate can create it unique from the start. Still route the change through the `oracle-db-admin` gate as a schema change.

   **Caveat on what the index buys:** `ProviderUserID` is `NullableDBVarchar`, and a NULL component makes a unique key non-conflicting on both Oracle and PostgreSQL. So the index prevents duplicates for real provider identities but does NOT constrain rows with a NULL/empty `provider_user_id` — precisely the placeholder rows the comment at main.go:2369-2379 refuses to create. Fixes 1 and 2 remain load-bearing; the index is defense in depth, not a substitute.

Fix 2 is worth doing regardless of 1 — it is the reason a read bug became a write bug.

## Environment
Oracle ADB 23ai, gorm-oracle v1.1.3 (uppercase naming strategy), found 2026-08-07 during the 1.8.1 Oracle test pass. Related: #699 (remaining lowercase-tag scan sites), #698, #696.


**Direction for this task:** implement all three fixes from the issue: (1) fix the ad-hoc scan struct in `findUserByProviderIdentityGorm` (cmd/server/main.go ~2433) so the projection/scan works on Oracle (follow the house pattern from api/group_member_repository.go:567-606 — untagged field or dialect-aware DBName, not a lowercase column: tag); (2) at the caller (~main.go:2361), distinguish `gorm.ErrRecordNotFound` from other errors — only not-found routes to the create branch, any other error aborts with the error; (3) make `idx_users_provider_lookup` UNIQUE via the one-tag change in api/models/models.go:35-36 (`uniqueIndex:idx_users_provider_lookup` on both fields). Add unit tests for the lookup/create decision logic where feasible.

## Task 3: Fix #710 — remove 41 lowercase gorm column: tags across api/models

### Issue #710: fix(db): lowercase gorm:"column:..." tags on 41 GORM model fields silently zero results on Oracle

## Summary
Issue #699 fixed the "ad-hoc scan struct with hardcoded lowercase `gorm:\"column:...\"` tags" bug class for four specific non-model scan structs. The same bug class also exists on GORM **models** themselves (registered types under `api/models/`, used with `AutoMigrate`/`Create`/`First`/`Find`/`Save`), which #699's scope explicitly did not cover. GORM matches Oracle's UPPERCASE result-set column labels to struct DBNames case-sensitively; a field pinned to a lowercase `column:` tag never matches, and the field silently reads back as its Go zero value on Oracle -- no error, no panic, just wrong data.

`rg -c 'gorm:"[^"]*column:[a-z]' api/models/*.go` finds **41 such fields**:
- api/models/models.go -- 26
- api/models/extraction_job.go -- 9
- api/models/survey_models.go -- 4
- api/models/system_setting.go -- 2

## Highest-severity instance: AliasCounter (api/models/models.go:962-966)

```go
type AliasCounter struct {
	ParentID   DBVarchar `gorm:"primaryKey;not null;size:36;column:parent_id"`
	ObjectType DBVarchar `gorm:"primaryKey;not null;size:16;column:object_type"`
	NextAlias  int32     `gorm:"not null;default:1;column:next_alias"`
}
```

Verified by reading `api/alias_allocator.go`'s `allocateNextAliasRowLocked` (used for per-scope sub-object aliases -- assets, threats, documents, notes, repositories, diagrams within a threat model):

1. It upserts a counter row (`ON CONFLICT DO NOTHING`), then does `tx.Clauses(clause.Locking{Strength: "UPDATE"}).Where(...).First(&counter)`.
2. On Oracle, the result labels come back `PARENT_ID`/`OBJECT_TYPE`/`NEXT_ALIAS`, which do not match the lowercase-pinned tags, so `counter.NextAlias` scans as the Go zero value `0` every time, regardless of the row's actual stored value.
3. `allocated := counter.NextAlias` is therefore always `0`. The bump then does `Update("next_alias", counter.NextAlias+1)` -- i.e. always writes `1` -- so the stored counter never advances past what the read reports.
4. Every allocation for a given `(parent_id, object_type)` returns alias `0` (or a repeating small value), so the **second** entity of that type in the same threat model collides on the `uniqueIndex:uniq_*_tm_alias` constraint -> **ORA-00001** (unique constraint violation) surfaced to the caller as an unexpected 500/409 on asset/threat/document/note/repository/diagram creation.

This is a live, high-severity bug for any Oracle ADB deployment exercising per-scope aliasing (shipped in 1.8.0), not a theoretical one -- confirmed by direct code reading, independent of the CATS/integration test suite (which runs against Postgres, where this is invisible).

## Other notable instances (not yet individually verified to this depth)
- `extraction_job.go` (9 fields) -- extraction job status/progress tracking; likely produces incorrect/zeroed job status on Oracle reads.
- `survey_models.go` (4 fields) -- survey JSON/UI-state blobs.
- `system_setting.go` (2 fields) -- `setting_key`/`setting_type`; could misroute config lookups on Oracle.
- `models.go`'s other 23 (beyond AliasCounter) span multiple entity types -- needs a full per-field audit like the one #699 did for its four sites.

The #699 fix added `scripts/check-scan-struct-column-tags.py` (wired into `make lint`), but it excludes `api/models/` on the assumption the directory already follows the untagged-field convention. That assumption is false -- this issue is the correction. The exclusion is being kept for now (removing it would fail `make lint` immediately with 41 pre-existing violations out of #699's scope) but the guard's comment has been corrected to reference this issue instead of asserting the directory is clean.

## Task 4: Fix #711 — pin the DBMS_LOCK advisory lock to a single Oracle session

### Issue #711: fix: DBMS_LOCK advisory lock is not pinned to a single Oracle session

## Context
Found during oracle-db-admin review of #704 (groups unique-index dedupe, branch dev/1.8.2/oracle-followups).

`acquireOracleLock` in `internal/dbschema/advisory_lock.go` issues `DBMS_LOCK.ALLOCATE_UNIQUE`, `DBMS_LOCK.REQUEST`, and `DBMS_LOCK.RELEASE` as three separate `sqlDB.ExecContext` calls against the shared `database/sql` connection pool. `DBMS_LOCK` ownership is **session-scoped** in Oracle, and `database/sql` gives no guarantee that those three calls land on the same physical Oracle session (the pool can hand out a different connection for each `ExecContext`). As a result, the lock may end up requested and released against different sessions, or the release could silently no-op against a session that never held it — meaning the cross-replica migration lock this function is supposed to provide may not actually be exclusive on Oracle.

This is a pre-existing defect (not introduced by #704), but #704's `DeduplicateGroups` pre-AutoMigrate dedupe step now explicitly depends on the stated safety argument that it "runs under the same advisory lock as AutoMigrate" to avoid a cross-replica race. The mitigating factor is that `DeduplicateGroups` is itself written to be concurrency-tolerant (deterministic survivor selection by `first_used, internal_uuid`, plus a `len(rows) < 2` re-check inside its own transaction), so two replicas racing would converge rather than corrupt data — but the underlying lock gap should still be closed.

## Suggested fix
Acquire the Oracle advisory lock via a pinned connection (`sqlDB.Conn(ctx)`) and run `ALLOCATE_UNIQUE`/`REQUEST`/work/`RELEASE` all on that same `*sql.Conn`, rather than through the general pool.

## Where
- `internal/dbschema/advisory_lock.go` (`acquireOracleLock`, lines ~73-120)

**Direction for this task:** implement the suggested fix: in internal/dbschema/advisory_lock.go, acquire a dedicated connection via `sqlDB.Conn(ctx)` and run ALLOCATE_UNIQUE / REQUEST / (hold for the duration of the locked work) / RELEASE on that same *sql.Conn, closing it after release. Preserve existing timeout/error semantics and keep the lock held across the whole migration critical section exactly as the current call contract expects (check the caller in cmd/server/main.go / internal/dbschema to keep the handle alive rather than acquiring and instantly releasing). Add/adjust unit tests where feasible (the Oracle path may only be exercisable by construction — structure the code so the pinned-connection invariant is testable or self-evident).

## Task 5: Fix #712 — bounded retry around groups dedupe transactions on transient errors

### Issue #712: fix: no bounded retry around groups dedupe transactions on transient Oracle errors

## Context
Found during oracle-db-admin review of #704 (groups unique-index dedupe, branch dev/1.8.2/oracle-followups).

`DeduplicateGroups` calls `dedupeGroupKey` once per duplicate `(provider, group_name)` key, each in its own `db.Transaction(...)`, with no retry wrapper. If two replicas race to dedupe overlapping keys (or the same key) concurrently, Oracle can return ORA-00060 (deadlock) or ORA-08177 (serialization failure), both of which `internal/dberrors.Classify` already maps to `ErrTransient`. Today that error propagates straight out of `DeduplicateGroups` to `runMigrationsLocked` in `cmd/server/main.go`, which returns an error and the caller does `os.Exit(1)` — turning a normally-recoverable transient contention error into a boot crash-loop instead of a retry-and-succeed.

Likelihood is low: `dedupeGroupKey`'s per-key row ordering is deterministic (earliest by `first_used`, tie-broken by `internal_uuid`), and duplicates are expected to be rare and shrinking over time. But the *outer* iteration order over duplicate keys (`dups`) is not deterministic (`GROUP BY` output order is unspecified on Oracle), so a cross-key deadlock between two replicas processing different keys in different orders isn't structurally impossible.

## Suggested fix
Wrap `dedupeGroupKey`'s transaction in a small bounded retry when `dberrors.IsRetryable(err)` (which is already `true` for `ErrTransient` and correctly `false` for `ErrDuplicate` — see `internal/dberrors/errors.go`). `auth/db.WithRetryableGormTransaction` may be usable directly, or a lighter local retry loop, depending on whether `internal/dbschema` can cleanly depend on `auth/db` (check for import cycles first).

## Where
- `internal/dbschema/group_dedupe.go` (`dedupeGroupKey`, called from `DeduplicateGroups`)
- Call site: `cmd/server/main.go` (`runMigrationsLocked`)

**Direction for this task:** implement the suggested fix: wrap `dedupeGroupKey`'s transaction (internal/dbschema/group_dedupe.go) in a small bounded retry triggered only when `dberrors.IsRetryable(err)`. Check for an import cycle before reusing `auth/db.WithRetryableGormTransaction`; if it would cycle, write a small local bounded-retry loop (e.g. 3 attempts with short backoff) using internal/dberrors classification. Non-retryable errors propagate unchanged. Add a unit test for the retry behavior (retryable error retried then succeeds; non-retryable fails immediately).

## Task 7: Fix #718 — OAuth resolver must not 500 on unique-index conflict (follow-up to #701)

### Issue #718: fix(auth): OAuth tiered user resolver treats any lookup error as not-found, now reachable as a 500 after #701's unique index

## Summary
`findOrCreateUserWithResolver` (auth/handlers_oauth_user.go:110-196) has the same error/not-found conflation bug that #701 fixed in the admin-config lookup path: every tier (`GetUserByProviderID`, `GetUserByProviderAndEmail`, `GetUserByEmail`) treats ANY error — not just "no row" — as "no match," and falls through to `CreateUser` on the next tier's failure.

Discovered during the oracle-db-admin review of #701's fix (making `idx_users_provider_lookup` a UNIQUE index on `(provider, provider_user_id)`). Before that index existed, a transient Oracle read failure at tier 1 (e.g. ADB idle-connection kill: ORA-03113/ORA-03114/ORA-12537, or contention: ORA-00060/ORA-08177) fell through to `CreateUser`, which succeeded and silently produced a duplicate USERS row (200 OK, wrong data). After #701's unique index, that same insert now hits the new unique index, producing ORA-00001, classified `ErrDuplicate` by `internal/dberrors`, and surfaced by `auth/handlers_token.go:242` as an unconditional HTTP 500. The same 500 is also reachable without any transient error: two concurrent OAuth callbacks for a brand-new `(provider, sub)` (SPA double-submit / retry-on-timeout) race on `CreateUser`; the loser now 500s where it previously silently duplicated.

This violates the repo's MANDATORY Zero-500-Error Policy and is more likely on Oracle ADB than PostgreSQL because of ADB's idle-connection behavior.

## Suggested Fix (two independent halves; do both)
1. Mirror the #701 caller fix in the resolver: only `errors.Is(err, gorm.ErrRecordNotFound)` (or the store-layer equivalent, e.g. via `internal/dberrors` classification if the resolver methods wrap errors) may fall through to the next tier; any other error should abort the login attempt with a distinct classified error rather than being treated as not-found.
2. Make `CreateUser` failure recoverable: on `errors.Is(err, dberrors.ErrDuplicate)`, re-run the tier-1 lookup once and return that row (the "insert lost the race, read the winner" pattern used elsewhere in this codebase, e.g. #705) instead of bubbling a 500.

## Scope note
This is a pre-existing latent bug (silent duplicate creation on transient errors), not introduced by #701. #701's unique index changes its failure mode from "silent duplicate + 200" to "500," which is why it needs fixing now rather than later. Out of scope for #701 itself because it lives in a different, security-sensitive file (four-tier matching with cross-provider-conflict rejection, #290) that deserves its own focused change and test coverage.

## Related
#701, #705 (same "re-read the winner after a lost upsert race" pattern), #290 (cross-provider conflict rejection logic this touches)
